# Feature: Snakemake Pipelines, QC Gates and Summaries <!-- rq-03cab891 -->

Every study with stages runs end-to-end with one Snakemake command. Nobody writes Snakemake rules:
the study's `Snakefile` is a fixed stub that asks `tophat` to generate the rules from the study's
configuration every time Snakemake starts. Generated rules run each stage in its pixi environment,
seal its output (see `rqm/pipeline/provenance.md`), fan out over items where configured, stop at
human QC gates, and finally write `SUMMARY.md`, from which `tophat study report` copies results
(see `rqm/study/format.md`).

## Running a Study <!-- rq-1339368c -->

From the project root:

```
pixi run snakemake -s studies/<study>/Snakefile --cores <n>
```

The default target is `summary`, which builds every stage for every variant listed in `STUDY.md`
and then writes `SUMMARY.md`. The target `variant_<variant>` builds every stage of one variant
without writing the summary. `tophat run` (see `rqm/workflow.md`) wraps this command.

For a study with status `draft`, the generated rules contain only the **trial** targets `trial`
(every variant) and `trial_<variant>`, which build trial outputs (see `rqm/workflow.md`) and never
write the summary. For every other status they contain the targets above and no trial targets.

## The Snakefile Stub <!-- rq-fbc524b4 -->

`studies/<study>/Snakefile` has exactly this content, with `<study>` replaced by the study ID:

```python
# Generated by tophat for study <study>. Do not edit: `tophat check` rejects changes.
# The rules are regenerated from config/ every time Snakemake starts.
import subprocess
from pathlib import Path

_rules = Path(workflow.basedir).parents[1] / ".tophat" / "generated" / "<study>.smk"
subprocess.run(["tophat", "pipeline", "rules", "<study>", "--output", str(_rules)], check=True)
include: str(_rules)


rule tophat_default:
    default_target: True
    input: _TOPHAT_DEFAULT_INPUTS
    run:
        _tophat_default()
```

Snakemake never takes its default target from an included file, so the stub defines it. The
generated rules define `_TOPHAT_DEFAULT_INPUTS` and `_tophat_default` so that the default does what
the `summary` target does (or, for a draft study, what the `trial` target does).

`tophat study new` writes the stub, and `tophat pipeline stub <study>` rewrites it. The directory
`.tophat/generated/` is git-ignored.

## Generated Rules <!-- rq-56d46fa3 -->

`tophat pipeline rules <study> --output <file>` writes a Snakemake rules file for every variant
listed in the study's `STUDY.md`. Generation fails, writing nothing, when the configuration has a
`pipeline.config-invalid`, `pipeline.code-missing` or `pipeline.env-missing` error, or a referenced dataset is unknown, retired, in an unconfigured root, or has a
file missing or of the wrong size. The output is deterministic for a given project state.

### One job per key <!-- rq-5782f3d0 -->

- Each distinct `(stage, key)` across the variants is one rule, named `<stage>_<key without "sk-">`
  (`trial_<stage>_<key without "sk-">` for trial rules). Variants that share a key share the job and
  its output.
- Trial rules use the trial output locations, seal with `--trial`, and have no QC inputs.
- A rule's output is `<output directory>/provenance.json`. A sealed output is never re-run:
  upstream outputs are inputs whose modification times do not trigger re-runs, and nothing else
  that Snakemake tracks enters the rule.
- A rule's inputs are the `provenance.json` of each `stage:` input (for a fan-out upstream, its
  stage-level record).
- A rule's action, in order:
  1. For each gated upstream stage, check its verdict for the upstream key (see *Validation and
     Review*); stop with an error if it is missing or `fail`.
  2. Empty the output directory (create it if absent), removing any partial results of a failed run.
  3. Run the stage's `run` command, with placeholders substituted, from the study directory in its
     pixi environment (`pixi run --frozen -e <env>`; for a tool stage, with `--manifest-path` of
     the tool environment, see `rqm/pipeline/tools.md`).
  4. Run the stage's `validate` command, if any, the same way; when it fails, stop without sealing.
  5. Run `tophat stage seal` with the study, stage, key and variant.
- The rule's `threads` are the stage's `threads`.

### External stages <!-- rq-4acafba4 -->

The job of an external stage (see `rqm/pipeline/external.md`) checks the verdicts of gated upstream
stages like any job, then runs `tophat stage external`. While the job has not been returned, that
command writes the bundle, prints the instructions and fails, so Snakemake stops there; once the
receipt and outputs have been copied back, it ingests and seals the stage and downstream stages
continue.

### Fan-out <!-- rq-a44c3b76 -->

For a stage with `foreach: <input>`:

- The **items** are the regular files directly inside the input's directory: for a `stage:` input,
  its output directory (excluding `provenance.json` and names starting with `.`); for a
  `dataset:` input, the manifest's top-level files. Item names are file names without their last
  extension. Items are known only after a `stage:` input is sealed, so that upstream rule is a
  Snakemake checkpoint.
- One job per item runs the stage with `{item}`, `{item_name}` and `{out}` set for that item
  (`{out}` is `<output directory>/items/<item name>/`) and seals it with `--item`.
- A gather job, run after every item job, seals the stage without `--item`, writing the stage-level
  record. Downstream stages depend on the stage-level record, and `{in.<stage>}` is the stage's
  output directory, containing `items/<item name>/` per item.
- Two items with the same name, or a name not matching `^[A-Za-z0-9._-]+$`, fail the gather job
  with a message naming them.
- If one item fails, Snakemake retries only that item; sealed items are kept.

### Summary rule <!-- rq-bdfef246 -->

The `summary` rule depends on the stage-level non-trial record of every stage with `result`, for
every listed variant, and runs `tophat study summarize <study>`. `STUDY.md` is never an input of any
rule.

## Validation and Review <!-- rq-dc1e521d -->

A stage's output is checked in two ways: by code every time, and by a human where judgment is
needed.

**Validation** is mechanical and automatic. A stage may declare `validate`, a command with the
placeholders of `run`, that checks the stage's output and exits non-zero when something is wrong:
missing files, wrong shapes, missing or non-finite values, values out of range. It runs after the
stage's command succeeds, from the study directory in the same environment; when it fails, the job
fails and the output is not sealed. Because it decides what is sealed, the `validate` command
enters the stage key (see `rqm/pipeline/provenance.md`). External stages cannot declare `validate`:
their output is sealed when the returned job folder is ingested; scenario tests check them.

**Review** is a human judgment, opt-in per stage. A stage that declares `review`, the question a
human answers by looking at the output (for example "Do the filtered signals look like smoothed
steps, without the noise spikes?"), is **gated**: it needs a human verdict before any stage that
consumes it runs, and before the study can be reported. Stages without `review` have no gate.
Review is for what code cannot decide: whether a plot looks right, whether a fit is sensible,
whether an intermediate result makes scientific sense.

- The verdict is the committed file `studies/<study>/qc/<stage>/<key>.md`:

  ```markdown
  ---
  stage: score
  key: sk-3f9a1c2b4d5e6f70
  verdict: pass
  date: "2026-10-20"
  ---

  Looked at energy distributions for all 200 items; two outliers explained by ...
  ```

- Verdict files are not Snakemake inputs (a regenerated upstream output would otherwise force a
  rule to "produce" a verdict that only a human can give). Instead, each job that consumes a gated
  stage checks the verdict before doing anything else, and `tophat study report` refuses while a
  gated stage of a listed variant has no `pass` verdict for its current key.
- Until the file exists, that check fails with a message telling the human to run
  `tophat stage qc <study> <stage> --variant <variant>`, so Snakemake stops before the downstream
  stages run any command.
- When the verdict is `fail`, every downstream job fails immediately with a message naming the QC
  file; nothing downstream runs.
- A QC verdict belongs to one key. A new key (any change upstream or to the stage) needs a new
  verdict.

## Summaries <!-- rq-1a4b027f -->

`tophat study summarize <study>` writes `studies/<study>/SUMMARY.md` (format in
`rqm/study/format.md`):

- One result line `- <variant>/<stage>: <text>` per listed variant (in `STUDY.md` order) and per
  stage with `result` (in stage order), `<text>` being the single line of that stage's result file
  in its sealed output for the variant's current key.
- `commit` is the project's `HEAD`.
- `dirty` is `true` if any provenance record the result lines derive from is not clean: the result
  stage's record and, transitively through `stage:` inputs, every upstream record, including each
  fan-out item's record.
- `keys` maps each `<variant>/<stage>` result line to the key it was read from.
- `generated` is the current time and `tophat_version` the running version.

## Feature API <!-- rq-0a8079d6 -->

### Commands <!-- rq-d7fc4287 -->

- `tophat pipeline rules <study> --output <file>` <!-- rq-654fa516 -->
  - Generates the rules file as specified under *Generated Rules* and writes it atomically,
    creating parent directories. Exits non-zero, writing nothing, when generation fails.
- `tophat pipeline stub <study>` <!-- rq-c7d50a4a -->
  - Writes the `Snakefile` stub for the study, replacing any existing file.
- `tophat stage qc <study> <stage> [--variant <variant>]` <!-- rq-6c24fee9 -->
  - Requires standard input and standard output to be interactive terminals, like
    `tophat study preregister`; the verdict is a human decision.
  - Requires the stage to be gated (to declare `review`), a sealed non-trial output for the variant's
    current key (default variant `base`), and no existing verdict file for that key.
  - Prints the stage's `review` question and a summary of the output (key, number of files, total
    size, number of items, whether the record is clean, and the output directory), then asks the
    user to type `pass` or `fail` and a one-line note. Any other verdict text aborts without
    changes.
  - Writes the verdict file atomically with today's local date.
- `tophat stage qc-status <study> <stage> --key <key>` <!-- rq-872c3d40 -->
  - Exits 0 if the verdict file for the key says `pass`, 1 if it says `fail`, and 2 if it is
    missing or invalid, printing which. Used by generated rules.
- `tophat study summarize <study>` <!-- rq-23fa4a9a -->
  - Writes `SUMMARY.md` as specified under *Summaries*. Fails, writing nothing, if the study has no
    stage with `result`, any required output is not sealed under its current key (listing them),
    a result file does not have exactly one non-empty line, or the project is not a git repository.

### Functions <!-- rq-5ea916b5 -->

- `generate_rules(root: &Path, study: &str) -> Result<String, PipelineError>` — the rules file text. <!-- rq-aa6553ad -->
- `stub(study: &str) -> String` — the exact `Snakefile` stub text. <!-- rq-3c19a18d -->
- `summarize(root: &Path, study: &str) -> Result<Summary, PipelineError>` — computes the summary <!-- rq-b9512459 -->
  that `tophat study summarize` writes.

## Check Rules (`pipeline` family, execution) <!-- rq-7b0b2ae8 -->

| Rule | Severity | Condition |
|---|---|---|
| `pipeline.snakefile-missing` | error | A study with stages has no `Snakefile` |
| `pipeline.snakefile-modified` | error | A study's `Snakefile` differs from the stub |
| `pipeline.qc-invalid` | error | A file under `qc/` is not `qc/<stage>/<key>.md`, cannot be parsed, has a `stage` or `key` disagreeing with its path, a `verdict` other than `pass` or `fail`, or names a stage that is not gated in any variant |
| `pipeline.summary-stale` | warning in `draft`; error in `preregistered` and `reported` | `SUMMARY.md` has `keys` and an entry differs from the current key of that variant and stage, or names a result stage or variant that no longer exists |

## Assumptions <!-- rq-b4d5c830 -->

- Snakemake and pixi are installed in the project environment; `tophat` is on `PATH` inside it.
- Snakemake is always run from the project root.
- A study ID is a valid path segment, so the stub's paths need no quoting.

## Out of Scope <!-- rq-c0a68ab3 -->

- Snakemake cluster or executor profiles.
- Cleaning up output directories of old keys.
- Generating rules for studies of other projects.
